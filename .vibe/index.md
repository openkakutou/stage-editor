# stage-editor — Codebase index

## Modules
- [`modules/app.md`](modules/app.md) — application entry point, builds the app's `web-ui-kit` root frame (toolbar + the stage file input, characteristics editor, BG element editor, and Save/Export button as main content) and mounts it into the DOM
- [`modules/input.md`](modules/input.md) — the stage folder input: gathers files from a folder selection/drag-and-drop, picks the `.def` candidate, loads it via the WASM bridge, and resolves its referenced sprite sheet from the same folder by basename; also renders the folder-picker/drag-and-drop UI. Ported verbatim from `stage-viewer-web`'s own `src/input/`
- [`modules/document.md`](modules/document.md) — holds the currently loaded stage in memory, the single place later editor screens read from and write back to
- [`modules/editor.md`](modules/editor.md) — the editing screens (a characteristics editor, name/author/camera bounds/stage boundaries; a BG element editor, add/edit/remove with sprite reference validation) and the save flow (serializes the document and triggers a download, or shows a clear error)
- [`modules/wasm.md`](modules/wasm.md) — bridge to the `stage` WASM module (write mode): loads it client-side and exposes typed `loadStage`/`saveStage` wrappers, plus the `StageData` TypeScript vocabulary, each returning a typed result instead of throwing
- [`modules/sff-wasm.md`](modules/sff-wasm.md) — a second, independent bridge to the `sff` WASM module: sprite sheet metadata only, used to validate a BG element's sprite reference
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `stage` and `sff` WASM release builds

## Observed patterns
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderStageFileInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap — same "inject external effects for testability" shape as the WASM bridge and download script, applied here to DOM construction instead of `fetch`
- No UI affordance is added for a capability that doesn't exist yet — a disabled or purely-visual stub is treated as worse than no affordance at all; once the capability lands (e.g. save), the real affordance replaces the absence directly, not a stub-then-swap
- A component that always reads its data source fresh at the moment it's actually needed (Save/Export re-reading the document store on click, not on render) needs no dirty-state tracking or explicit re-render wiring to stay correct after an edit made elsewhere
- In-process application state with no external effect to substitute in tests (the currently loaded document) is a plain module-level variable behind a get/set pair with a test-only reset, not a class or an injected dependency — same shape as `wasm/bridge.ts`'s own memoized WASM instantiation
- Setting a new value into a module-level store is always a full replace, never a merge, and never gated by a confirmation prompt while nothing built on top of it can yet lose unsaved state — a future consumer that adds real mutation is the one responsible for adding a discard-changes guard at its own call site, not the store
- A generic, domain-agnostic module (folder/drag-drop gathering) is ported verbatim between sibling repos rather than re-derived or abstracted into a shared package; a module with real domain logic (sprite-sheet resolution) is also ported verbatim once already validated elsewhere, with the original rationale referenced by pointing at the sibling repo's own ADR rather than duplicating it
- Any app-level visual value (typography hierarchy, spacing) is expressed only through `@openkakutou/web-ui-kit`'s `--wuik-*` CSS custom properties, never a literal px/hex value
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs` (not bundled/type-checked by `tsc`, whose `include` is scoped to `src/`)
- `wasm_exec.js` (a plain global-side-effect script, not an ES module) is executed via `new Function(source)()` rather than a `<script>` tag or dynamic `import()`, so the same loading code works identically in a real browser and under jsdom/Node
- A field whose Go source is a nil-by-default slice is typed as `T[] | null` in TypeScript, not `T[]` — matches `encoding/json`'s actual nil-slice-marshals-to-`null` behavior instead of assuming an empty array
- A write-path wrapper (`saveStage`) that re-parses a byte buffer internally is tested for its own malformed-input error path, not assumed to inherit `load`'s — read the underlying Go source (`save.go`) to confirm this before writing the test, rather than guessing from the read-path's behavior
- A referenced filename that a real-world text format writes inconsistently (directory prefix, separator style, letter case) is resolved by basename, exact match first, case-insensitive fallback second, rather than a byte-for-byte string comparison; more than one match is reported as ambiguous rather than silently picked
- File bytes are read via `FileReader` rather than `Blob#arrayBuffer()` — this project's pinned jsdom doesn't implement the latter
- Non-standard browser APIs jsdom doesn't implement at all (`FileSystemEntry`, `DataTransferItem.webkitGetAsEntry()`) are modeled as minimal `*Like` interfaces so the drag-and-drop walk logic is unit-testable against plain mock objects, with real browser behavior confirmed separately via real-browser verification
- Clicking a radio input in a test is read via a `"click"` listener, not `"change"` — this project's pinned jsdom doesn't reliably synthesize `"change"` after a dispatched `"click"`
- Fixture-driven tests that exercise the real WASM module pin expected values obtained by running the actual module once against the fixture, sharing a minimal `.def` fixture with `stage-viewer-web`'s own `src/wasm/testdata/` rather than depending on a sibling checkout at test time
- Real-browser verification of a file-input feature drives an actual `<input webkitdirectory>` selection against a real folder on disk (Playwright's `setInputFiles` accepts a directory path directly) rather than only simulated `FileList`/entry mocks
- An editor screen mutates the caller-owned document object in place rather than returning a patch, with an optional `onChange` observer only for callers/tests that want to react — same shape `lifebar-editor`'s own `elements-editor.ts` established
- A field irrelevant to the current value of a discriminant field (a BG element's sprite reference when its type is "anim") is hidden, never shown-but-disabled, and its own underlying value is never cleared when it's hidden — only stops being rendered/used, so toggling the discriminant back restores it unchanged
- "Has this been edited" is tracked per object by reference (a module-level `WeakSet`), not by comparing current values to their defaults — a value-equality heuristic a user could accidentally satisfy by typing back to the same number
- Only a structural list change (add, remove, a type switch that changes which fields render) triggers a full list re-render; a plain field's own commit (always on `blur`, so focus has already moved elsewhere) updates just that item and its own summary text in place, so a full rebuild never interferes with the browser's own focus-move sequencing mid-Tab
- Two Go WASM modules from different producer repos are bridged independently rather than one being taught the other's surface, when the second module already ships the exact capability needed (`sff`'s own sprite metadata) and the first's own backlog item for it would add unrelated capability (pixel decode) the app doesn't need — each module's release assets (including its own `wasm_exec.js`) download into a separate subdirectory so the two never collide, since a `wasm_exec.js` is only guaranteed compatible with the Go toolchain version that built its own paired `.wasm` binary
- A file download is triggered via a throwaway `Blob` + `URL.createObjectURL` + a programmatically-clicked `<a download>`, immediately revoked after — ported verbatim from `character-editor`'s own established pattern rather than re-derived
- An acceptance criterion phrased more strongly than an already-established, deliberate, cross-repo serialization contract actually guarantees ("only that field's line(s) changed") is satisfied under the contract's real, documented behavior (byte-identical only when nothing changed; a full fresh — but correct — reserialize on any edit) rather than treated as a gap to fix locally; reopening that contract is a cross-repo architectural question, not this item's call to make unilaterally
