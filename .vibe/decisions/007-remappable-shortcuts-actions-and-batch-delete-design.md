# Remappable shortcuts: which actions, default keys, and the new batch-delete action's own design

**Context:** Item 009 adopts `web-ui-kit`'s `ShortcutManager`/`<wuik-shortcuts-panel>` for this app's actions, deferred by `.vibe/decisions/006`. The backlog's own acceptance criteria explicitly name five actions: save, undo, redo, add BG element, delete selection. The first four already exist as clickable controls; "delete selection" does not — the BG element batch toolbar (item 007) only offers Clear selection, Apply offset, and Apply sprite reassignment, with no single action that removes the whole current multi-selection at once. Several points needed a call: default keys, whether Undo/Redo/Delete's shortcut should fire while typing in a text field, whether a checkbox counts as "typing" for that guard, and whether the new batch-delete needs its own confirm step given it has no existing UI to point to.

**Decision:**
- Default keys: Save/Export `Ctrl+S`, Undo `Ctrl+Z`, Redo `Ctrl+Y`, Add BG Element `Ctrl+Shift+A`, Delete Selection `Delete`.
- Save/Export and Add BG Element always fire regardless of focus — neither key has a native in-field editing meaning to preserve (Ctrl+S only needs the browser's own "Save Page" dialog suppressed; Ctrl+Shift+A has no browser/OS meaning at all).
- Undo, Redo, and Delete Selection are suppressed whenever focus is inside a genuine text-entry control (a text-like `<input>`, a `<textarea>`, or a contenteditable region) — but *not* merely because focus sits on a `<input type="checkbox">`. A checkbox is how a user builds the very selection Delete Selection acts on; treating it as "editable" would silently block the natural select-with-checkboxes-then-press-Delete flow, the opposite of this repo's own established `isEditableTarget` (ported from `lifebar-editor`, which treats every `<input>` as editable regardless of `type`) — refined here rather than reused verbatim.
- A new "Delete N selected" button joins the batch toolbar's existing three actions, `variant="danger"` and visually separated (pushed to the end, divider) from the other three. It has **no confirm step** — deletion is instant, with the app's existing Undo (already reachable via toolbar button and now Ctrl+Z) as the sole recovery path. An inline status message ("Deleted N element(s). Use Undo to restore.") is shown in the panel afterward as a visible recovery cue, reusing the `role="status"` idiom `save-export.ts` and the batch toolbar's own selection-count line already use — not a new toast/notification subsystem.
- The Keyboard Shortcuts panel section starts expanded (the only discovery path for a brand-new capability, per the same reasoning as `lifebar-editor`'s own equivalent decision) and sits at the bottom of the main content, after Save/Export — not above it, so it doesn't push more load-bearing content down the page on first paint.

**Reason:** The four pre-existing actions just need a second, rebindable trigger for a handler that already exists; only Delete Selection is a real new capability, so its own UX needed a deliberate call rather than an assumed-safe port. Ctrl+S/Ctrl+Shift+A always firing mirrors the existing project convention (`.vibe/decisions/006`'s underlying `lifebar-editor` precedent) that a guard is scoped to what the specific key would otherwise do, not applied uniformly. The checkbox carve-out fixes a real regression the naive verbatim port would introduce: the single most likely place focus sits right before a user wants to press Delete is the last checkbox they clicked. No confirm on batch delete was chosen over a two-step inline confirm (the single-row Remove control's own pattern) because this app already has a stronger, general-purpose safety net (full undo/redo, just wired to a shortcut in this very item) that a single-row remove didn't have when its own confirm step was designed — duplicating a confirm dialog on top of that would be redundant friction; the status message closes the remaining "was this actually recoverable" trust gap without inventing new UI infrastructure.

**Rejected alternatives:**
- *Reuse `lifebar-editor`'s `isEditableTarget` verbatim (any `<input>` regardless of `type`)*: rejected — would suppress Delete Selection precisely when focus is on the checkbox the user just used to build the selection, defeating the feature's main keyboard flow.
- *Give batch delete the same two-step inline confirm as single-row Remove*: rejected — this app's own Undo is a strictly stronger safety net (full restore, not just "are you sure"), already one keystroke away; a confirm dialog on top adds friction the row-level control never needed to justify precisely because it lacked that stronger net at design time.
- *A transient toast with an inline "Undo" button, floated per the UX consultation's suggestion*: rejected — this app has no toast/notification component anywhere; building one to close a single recoverability gap is disproportionate when a `role="status"` line achieves the same visible confirmation with the pattern already established twice in this same file.
- *`Insert` as Add BG Element's default key*: rejected per UX consultation — `Insert` is absent or Fn-shifted on many laptop keyboards, unlike `Ctrl+Shift+A`, which is reliably reachable everywhere.
