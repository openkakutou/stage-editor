# BG element batch editing: selection model, toolbar placement, and scope

**Context:** Backlog item 007 needed a multi-select mechanism for the BG element editor's row list, and its acceptance criteria's "a shared layer-order shift or sprite reassignment" left an open choice between two different batch actions. A `vibe:expert-ui-ux` plan consultation raised two implementation risks worth settling explicitly before writing code: how selection survives a row being added/removed mid-session, and where a batch toolbar can safely live given the list has no internal scroll container.

**Decision:**
1. **Selection is tracked by element object reference** (`Set<BGElement>`), not by array index — the same object the document's `elements` array already holds, mirroring `touchedElements`'s existing `WeakSet<BGElement>` convention in this same file. Removing a row deletes it from the set directly; no reindexing logic is needed, since nothing here depends on an index remaining stable across the array's own mutations. Converting to the index-keyed form `bg-element-batch-edit.ts`'s pure functions expect happens once, at the moment "Apply" is clicked (`elements().indexOf(el)`), always against the array's current state.
2. **The batch toolbar renders at the top of the panel**, not sticky-positioned, and only when the selection is non-empty. Sticky positioning would need the row list to first gain its own internal scroll container — a layout change unrelated to selection logic, out of this item's scope. Top-of-panel is at least reachable via scroll-to-top from anywhere in a long list, which the "Add element" button at the bottom already isn't.
3. **Sprite reassignment is the batch action shipped for the acceptance criteria's "layer-order shift or sprite reassignment" bullet.** A true batch reorder (moving the selection as a contiguous block earlier/later in the array, which is what actually determines draw order within a shared `layerNo`) is a well-defined, plausible future action, but is left for a separate pass rather than folded in here.
4. The toolbar shows the affected elements' names (capped, "+N more" beyond a few) before Apply, disables each Apply action until it has a non-default value to apply (a non-zero offset, or an actually-chosen sprite), and announces the selection count via `aria-live="polite"` — there is no undo yet in this app, so a batch action's scope must be self-evident before it commits.

**Reason:** Object-reference selection removes an entire class of stale-index bugs for free, at negligible cost (a plain `Set`, no reindex bookkeeping) — worth doing regardless of how rare row removal during an active selection actually is in practice. Deferring the scroll-container work keeps this item's diff focused on selection and batch-apply, its actual stated scope; a toolbar that only *pretends* to be sticky (nothing bounded for it to stick to) would be worse than an honest top-of-panel placement. Sprite reassignment over reorder is the narrower, unambiguous reading of the acceptance criteria's "or" — reorder's own UI (how does a user express "move this block of elements to here" without drag-and-drop, which this list doesn't have?) is a large enough question to deserve its own pass rather than a decision made silently, with no Product Owner available to confirm it in an autonomous run.

**Rejected alternatives:**
- *Index-keyed selection (`Set<number>`), matching `expandedRows`'s existing convention* — rejected: `expandedRows` already has a known gap (no reindex on removal), and propagating the same gap into a *destructive, batch-scale* operation is a materially worse failure mode than a stale expand/collapse index.
- *Sticky batch toolbar without a scroll container* — rejected: reviewed in the UX consultation as a false promise (nothing for `position: sticky` to stick within in a flat page-flow list) rather than a real improvement.
- *Batch layer-order shift instead of sprite reassignment* — rejected for this pass: well-motivated but needs its own selection-to-reorder interaction (button-driven "move up/move down as a block"? drag handles?) that deserves a dedicated design pass, not a decision folded silently into this item.
