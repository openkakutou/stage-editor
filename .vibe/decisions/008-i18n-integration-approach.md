# Localization (i18n) integration approach

**Context:** Backlog item 010 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `<wuik-locale-switcher>`, roadmap decision `023`) so this app's UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads. This exact feature already shipped in three sibling repos (`stage-viewer-web`'s own `.vibe/decisions/006`, `lifebar-viewer-web`'s own `.vibe/decisions/007`, `lifebar-editor`'s own `.vibe/decisions/009`); this decision adapts `lifebar-editor`'s approach (closest sibling: also a write-mode editor with undo/redo, a wizard, and a keyboard-shortcuts panel) to this app's specific screens.

**Decision:**
- The app's brand name ("Stage Editor") is left untranslated, treated as a proper noun — only descriptive text, status/error messages, and accessible labels move into the catalogs. Raw stage data (an element's name, its `type` enum value, numeric coordinates) is never passed through translation either — only the surrounding UI copy is.
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly, under this app's own namespace (`stage-editor`) and its own `localStorage` key (`stage-editor-locale`) — every OpenKakutou web app deploys as its own GitHub Pages project site under the same origin, so sharing `web-ui-kit`'s default key would leak one app's language choice into every other one. Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initAppI18n` has run yet — the existing test suite keeps asserting plain English text unchanged.
- `initAppI18n` is only ever called from the real bootstrap (`mount()` in `main.ts`), awaited before the first `renderApp` call — never from `renderApp` itself, which stays synchronous so tests can keep calling it directly.
- Live locale-switching is split by how much state a re-render would otherwise destroy, per screen:
  - The characteristics editor, the 3D model editor's static panels (headings/field labels/buttons), and the New Stage Wizard hold no locale-sensitive state a full re-render would lose — `main.ts`'s own `onLocaleChange` subscription (or the model editor's own already-existing `rerender()` closure, itself re-invoked from that same subscription) just re-invokes their existing render calls from the currently held data. The model editor's own live preview survives this untouched because its mounted container is re-parented, never recreated, by its existing session mechanism (`.vibe/decisions/004`).
  - The BG element editor keeps its selection (`Set<BGElement>`, by reference) and expanded-rows (`Set<number>`, by index) state exactly as `main.ts` already threads it through every other full-list rebuild trigger (a sprite sheet finishing decode) — a locale change becomes one more such trigger, calling the exact same `rerenderElements` closure.
  - The stage folder input keeps its currently-displayed status/error text as a small unformatted descriptor (not a pre-formatted string) and subscribes to `onLocaleChange` internally, re-formatting that descriptor plus every static label/hint/button text in place — mirrors `stage-viewer-web`'s own folder-input view.
  - The live 3D preview (`model-preview.ts`) owns real async/live state (a mounted three.js renderer, an in-flight glTF/HDR load) that a full re-render would tear down and restart. It only ever shows translated text in its own failure banner (WebGL unavailable, model load error); that banner recomputes its body text from a small stored "describe the current failure" closure and rebuilds just the banner on locale change, exactly mirroring `stage-viewer-web`'s own `model-preview.ts` handling — the mounted scene/camera itself is never touched.
  - The Undo/Redo and Save/Export buttons' shortcut-hint `title`/`aria-keyshortcuts` are recomputed directly by `main.ts` (the only place that knows both the translated base label and the shortcut manager's live binding) rather than by re-calling `bindShortcutLabel`, which would attach a second `"change"` listener on the shared manager on every language switch.
  - Save/Export's own status text (idle/saving/saved/error) is kept as a small stored descriptor, re-formatted in place on locale change, the same shape as the folder input above.
  - The Keyboard Shortcuts section's collapsed/expanded state is preserved by retranslating only its own header label in place from `main.ts`, without re-invoking the section's own render function (which would reset it to its own default, expanded, and would also require detaching/reattaching the shared `ShortcutManager` from a freshly created `<wuik-shortcuts-panel>` element for no reason).
- Keyboard shortcut action labels registered with the shared `ShortcutManager` (`APP_SHORTCUT_ACTIONS`, shown inside `<wuik-shortcuts-panel>`'s own rebind list) stay hardcoded English, matching `lifebar-editor`'s own identical, already-shipped precedent for the same shared component — it has no live-retranslation hook of its own, and this is a pre-existing gap accepted there, not a new one introduced here.
- Pluralized fragments (the BG element editor's "Deleted N element(s)") are phrased with an inline ternary suffix computed in code (`"Deleted {{count}} element{{suffix}}. Use Undo to restore."`, `vars: { count, suffix: count === 1 ? "" : "s" }`), the minimal change from the existing English-only logic, rather than i18next's automatic plural-key suffixing — consistent with `lifebar-editor`/`lifebar-viewer-web`'s own precedent of avoiding plural-rule handling entirely wherever a rephrasing avoids needing it.

**Reason:** Matching each screen's re-render strategy to how much state it owns is what keeps this feature from regressing the BG element editor's own careful selection/expansion handling and the 3D preview's own careful live-state handling (a mounted WebGL renderer, an in-flight async load) while still keeping the existing, already-large test suite passing with minimal, surgical edits — the fallback-mirrors-default-value property is what makes that possible for the majority of existing tests.

**Rejected alternatives:**
- *Re-run every screen's render function wholesale on every locale change, uniformly* — rejected: the BG element editor's selection/expansion and the 3D preview's mounted renderer/in-flight load are exactly the state a wholesale re-render can't tell apart from a first mount, and would visibly reset.
- *Re-call `bindShortcutLabel` again on every locale change instead of recomputing the hint directly* — rejected for the same reason `lifebar-editor` rejected it: that function's own `manager.addEventListener("change", ...)` call has no built-in idempotency, so repeated calls would attach a growing number of listeners onto the shared, long-lived `appShortcutManager` over a long session.
- *Translate the shared `ShortcutManager` action labels too, via a live re-registration on locale change* — rejected as out of scope for this item: `web-ui-kit`'s `ShortcutManager`/`<wuik-shortcuts-panel>` doesn't expose a supported way to update a registered action's label after the fact, and inventing one here would be a `web-ui-kit`-level change, not this app's own.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected for the same reason every sibling app rejected it: this org's shared GitHub Pages origin would leak one app's locale choice into every other OpenKakutou app on it.
