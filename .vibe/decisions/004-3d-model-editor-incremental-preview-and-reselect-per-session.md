# 3D model editor: incremental live preview, asset re-selection per session, values preserved on remove

**Context:** Item 006 adds a read+write editing screen for Ikemen GO 3D model-based stage settings (model/`.hdr` assignment, placement, camera, scaling, per-player start depth), with a live 3D preview. A mature read-only reference already exists in the sibling `stage-viewer-web` repo (its own item 006, `.vibe/decisions/005`): `three`, `<wuik-viewport-3d>` for camera math only, render-on-demand. Two consulting experts (real-time rendering, UI/UX) were brought in on the plan before implementation; their input shaped the decisions below.

**Decision:**
1. **The live preview mutates the already-loaded three.js scene in place for placement/camera edits, instead of tearing down and reloading on every field commit.** Assigning, replacing, or removing the model/`.hdr` file is the only thing that tears down and rebuilds the renderer/scene/PMREM environment (ported from `stage-viewer-web`'s mount/teardown shape, called once per real asset change). A committed Offset/Scale edit calls `position.set`/`scale.set` on the already-loaded model root; a committed Camera Near/Far/fov edit mutates the existing `PerspectiveCamera`'s fields and calls `updateProjectionMatrix()`; both simply flag the existing render-on-demand dirty bit rather than reloading anything. Per the real-time rendering consultation: HDR→PMREM regeneration is the dominant reload cost, and a fresh `WebGLRenderer` per field commit risks the browser's concurrent-context cap when a user tabs through several numeric fields quickly — neither is acceptable on every blur.
2. **The model/`.hdr` files must be (re-)selected by the user every editing session to preview or edit them.** This app's file input doesn't currently thread the originally-gathered folder listing through to the editor screens after mount (only `spriteSheetBytes` reaches `mountDocument`, not the full file list) — auto-locating an already-referenced model/`.hdr` from that folder, the way the read-only viewer does, is a separable plumbing change, not part of this item's scope. When a stage already references a model/`.hdr` by filename, the reference is shown as read-only text with a persistent, neutrally-worded inline notice ("select the file to preview or edit it") — worded as a statement of current capability, never as an error/warning, per the UI/UX consultation: a first-time Product-Owner user seeing a filename with no rendered preview would otherwise read it as broken, or worse, as the reference itself having been lost.
3. **Removing an assigned model or `.hdr` file clears only that file's own reference field.** Offset/Scale/Environment-Intensity and every other 3D field are left untouched, so re-assigning a model later doesn't discard previously-tuned values — the empty drop zone shows a one-line note that prior placement values are kept, so this is discoverable rather than assumed. Offset/Scale/Environment-Intensity fields are hidden entirely (not shown-disabled) while no model is assigned, matching this repo's own established "hide an irrelevant field, never clear its value" convention (`elements-editor.ts`); Camera/Scaling/PlayerStartZ fields stay visible and editable regardless, since they're plain data with no model dependency — the two groups get visually separate panels so a user isn't left wondering why some 3D fields work with no model assigned and others don't.
4. **No mismatch validation between a re-selected file's name and the stage's previously-stored reference.** Selecting a file always sets the reference to that file's own name — a legitimate "assign or replace", matching this repo's own established sprite-reference-by-basename precedent of trusting the user's own selection rather than second-guessing it.
5. **Removing a model/`.hdr` goes through the same inline confirm step `elements-editor.ts` already established** ("Remove this model?" / "Remove this lighting file?", a danger-styled confirm button plus cancel) rather than a native `confirm()` — always shown here (unlike that module's own "untouched element" single-click shortcut), since a file assignment has no meaningful "untouched" state to skip the confirmation for.
6. **Camera `YShift` is edited as plain data but never applied to the live preview.** The preview is a free orbit camera (`<wuik-viewport-3d>`), not Ikemen's actual in-game camera projection — matches the read-only viewer's own precedent of only consuming `fov`/`near`/`far` from `[Camera]`, never `yShift`.
7. **`[Scaling]` and per-player `Startz` fields never trigger a preview re-render.** Nothing in the model-only preview scene visually represents perspective scaling curves or player start positions (matches the read-only viewer's own scope), so wiring their commits to the dirty-flag would be a no-op trigger with no observable effect.

**Reason:** Each point traces to a concrete requirement or risk named by the two expert consultations (frame-budget and reload-cost risk from real-time rendering; discoverability and confusion risk from UI/UX) or to an existing, already-validated convention in this repo (`elements-editor.ts`'s hide-don't-clear rule and remove-confirm pattern) — not spec'd speculatively.

**Rejected alternatives:**
- **Full renderer/scene teardown and reload on every committed field edit** (the naive "just call the mount function again" approach): rejected per the real-time rendering consultation — the dominant cost (HDR→PMREM regeneration) would then run on every Offset/Scale/Camera blur, not just real asset swaps, and repeated `WebGLRenderer` construction risks the browser's concurrent-context cap.
- **Auto-resolving an already-referenced model/`.hdr` from the originally loaded folder**, mirroring the read-only viewer exactly: rejected for this item — the folder file list isn't currently threaded through to the editor screens post-mount, and doing so is a separate, non-trivial plumbing change with its own blast radius across every screen `mountDocument` wires up.
- **Clearing Offset/Scale/other 3D fields back to zero when the model/`.hdr` reference is removed**: rejected per the UI/UX consultation — would silently discard tuned values a user may want to keep for when a model is reassigned.
- **Validating that a re-selected file's name matches the stage's stored reference**: rejected as scope creep beyond this item's acceptance criteria and inconsistent with how sprite references are already trusted from user selection elsewhere in this app.
