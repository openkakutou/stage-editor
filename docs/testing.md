# Testing

## Running the suite

```sh
npm test        # single run
npm run test:watch   # watch mode
```

Vitest, `jsdom` environment. Test files are co-located with the source they test (`*.test.ts`/`*.test.mjs` next to the file it covers).

## Fixture-driven tests against the real WASM module

`src/wasm/bridge.test.ts` runs against the **real** `stage.wasm` module, not a mock — it reads `public/wasm/stage.wasm` + `wasm_exec.js` straight off disk via `node:fs` and injects them into the bridge's `fetchWasmExecSource`/`fetchWasmBytes` options, so no dev server or real network access is needed. Run `npm run wasm:download -- <version>` first if `public/wasm/` is empty (see `docs/development.md`).

A minimal `.def` fixture lives in `src/wasm/testdata/sample.def`, shared with (copied from) `stage-viewer-web`'s own fixture, itself copied from the `stage` repo's `cmd/wasm/testdata/sample.def`. `saveStage`'s tests were written after reading `stage`'s own `SerializeDef` source directly (`save.go`) rather than assumed: a non-empty original is re-parsed on every save call (a malformed original is a real `saveStage` error path, not just `loadStage`'s), and an edited stage that round-trips to the same normalized value as the original produces byte-exact output, otherwise fresh text is generated.

The stage folder input (`src/input/stage-file-input.test.ts`, `stage-file-input-view.test.ts`, and `main.test.ts`'s own store-integration cases) also runs against the real `stage.wasm` module the same way, ported verbatim from `stage-viewer-web`'s own equivalent tests — same fixture, same in-test `.sff` stand-ins (their content is never decoded by this item, so arbitrary bytes exercise name resolution and byte pass-through correctly). `main.test.ts` additionally exercises loading two different folders in sequence and asserts `stage-document-store.ts` holds only the second one — no merge, no leftover from the first.

`src/wasm/sff-bridge.test.ts` runs the same way against the real `sff.wasm` module (`public/wasm/sff/`, fetched via `npm run wasm:download:sff`), using a real `.sff` fixture (`src/wasm/testdata/v1-basic.sff`, copied from `lifebar-editor`'s own testdata) with one known sprite (group 0, image 0) — the exact metadata this fixture decodes to was obtained by running the actual module once, not derived from the mapping code under test.

## Editor screens

`characteristics-editor.test.ts` and `elements-editor.test.ts` exercise the two editing screens against plain in-memory `StageData`/`BGElement` fixtures — no WASM needed, since both screens are pure DOM-and-data-mutation logic. Coverage includes: every field pre-filled from the loaded stage; a text field committing live and a numeric field committing on blur (an invalid number is flagged inline and withheld, never silently coerced); the two bounds panels never bleeding into each other; an element's type switch showing/hiding only the fields that type uses, while preserving an unused field's own value in memory (verified by switching back); a sprite reference resolved against a real decoded sheet as valid, invalid, or not-yet-assigned (`-1,-1`, distinct from invalid); and the remove flow — a single click for an untouched, freshly-added element, an inline confirm/cancel step for one with a committed edit.

`save-export.test.ts` exercises the Save/Export button with the document store's own getter, `saveStage`, the download trigger, and `markStageDocumentSaved` all injected — covering: saving the document read fresh at click time and triggering a download with the original filename on success; clearing unsaved-changes tracking only on a successful save, never on a failed one; showing the WASM bridge's own error text (and never triggering a download) on a reported failure; and a no-op when clicked with nothing loaded. The round-trip fidelity properties themselves (byte-identical unedited, correctly-formatted-but-fresh output on an edit) are already proven at the bridge layer (`wasm/bridge.test.ts`'s own round-trip tests) and confirmed for this UI specifically by the real-browser pass below, not re-asserted here.

## New Stage Wizard

`new-stage-defaults.test.ts` exercises the pure stage builders directly: `createBlankStage()` produces a valid, non-degenerate coordinate space/camera bounds/boundaries with zero elements and a friendly default name; every entry in `STAGE_TEMPLATES` has a unique id, a non-empty label, at least one example BG element, and — specifically — never a fabricated sprite reference on those elements, only the established "not yet assigned" sentinel; every builder call returns an independently-mutable stage (mutating one call's result never leaks into another's).

`stage-document-store.test.ts` covers the snapshot-diff unsaved-changes tracking added for this item: clean right after loading, dirty once the loaded stage object is mutated in place, clean again if the exact original value is restored (proving it's a real value diff, not an edit-count flag), clean again after `markStageDocumentSaved()` despite the same edited object still being loaded, and clean once a brand new document replaces the edited one.

`new-stage-wizard.test.ts` exercises the wizard's DOM component with `onCreated`, `hasUnsavedChanges`, and `confirmDiscard` all injected — covering: both the "Blank Stage" and template buttons render and are labelled; creating immediately (no prompt) when nothing is dirty; prompting before discarding when something is dirty, and never creating anything (nor calling `onCreated`) when the prompt is declined.

`main.test.ts`'s own wizard-integration cases confirm the end-to-end wiring in the real app shell: the wizard renders from the very first paint (not gated behind a loaded file); creating a blank stage stores it and mounts the characteristics editor with no file ever loaded; focus moves into the characteristics editor's name field right after creation; and declining a real `window.confirm` prompt (spied, not injected, to prove the real default wiring) leaves the previously-edited document completely unchanged.

## jsdom gaps worked around in tests

`scripts/download-wasm.mjs`'s `--version` flag resolves its own `package.json` path via `fileURLToPath(import.meta.url)` (given the string form of the URL) rather than constructing a `new URL(...)` object first. Under this project's jsdom test environment, the global `URL` constructor is jsdom's own (a different realm from Node's), and `fs/promises.readFile` rejects a `URL` instance from that other realm with "The URL must be of scheme file" even though its `href` is a correct `file:` path — this sidesteps that entirely. Real `node scripts/download-wasm.mjs --version` on the command line is unaffected either way.

`src/input/`'s folder-gathering (`folder-entries.ts`) reads bytes via `FileReader` rather than `Blob#arrayBuffer()` — this project's pinned jsdom version doesn't implement it. jsdom also doesn't implement the non-standard `FileSystemEntry`/`DataTransferItem.webkitGetAsEntry()` APIs the drag-and-drop path uses at all, so `folder-entries.test.ts` exercises that walk against plain mock objects (`FileEntryLike`/`DirectoryEntryLike`) rather than real browser objects. Clicking a candidate-selection radio button in `stage-file-input-view.test.ts` reads the selection from a `"click"` listener rather than `"change"` — this project's pinned jsdom does toggle `.checked` on a dispatched `"click"` but doesn't reliably follow it with a `"change"` event.

## Beyond the test suite: real-browser verification

Passing tests are not treated as proof the UI renders correctly. The app shell was additionally driven against a real headless Chromium (dev server + Playwright) during development: confirming the toolbar reads "Stage Editor" (not carried-over "Stage Viewer" copy) with `web-ui-kit`'s actual computed styles applied, that no sidebar slot or save/dirty-state stub is rendered, and that `stage.wasm` is not fetched just from loading the page — the bridge only ever runs on demand. For the folder input specifically, the same real-browser pass drove an actual `<input webkitdirectory>` selection against a real folder on disk (Playwright's `setInputFiles` accepts a directory path directly), confirming the real WASM-backed load, the real sprite-sheet resolution, and — specific to this editor — that no premature "ready to edit" affordance appears and the status copy stays edit-neutral ("Loaded stage.def," never "Viewing").

For the characteristics and BG element editors (backlog item 003), the same real-browser pass loaded a real stage folder — a `.def` with two BG elements referencing a real `.sff` that only actually contains one of the two referenced sprites — and confirmed end-to-end: every field pre-filled correctly; editing the name and a camera bound committed for real; the element with the real sprite showed no invalid state, the one referencing the absent sprite showed the invalid-reference styling and message; switching that element's type to "anim" and back to "parallax" restored its parallax delta value unchanged; adding an element appended and auto-expanded it; removing an untouched element worked with one click; removing an edited element required the inline confirm step, and cancelling left it in place.

For save/export (backlog item 004), the same real-browser pass loaded a real stage folder, clicked Save/Export immediately (no edits), and captured the real download via Playwright's download event: byte-identical to the original file, downloaded under the original filename. It then edited the stage's name via the characteristics editor and saved again: the new download's `[Info]` section reflected the edit, and every other section round-tripped through a full fresh serialize (correctly formatted, per `stage`'s own documented contract for an edited save — see `.vibe/decisions/002-single-field-edit-produces-a-full-fresh-serialize-not-a-line-patch.md`) rather than a line-level patch. This isn't part of `npm test`; it's a manual verification step recorded in the relevant backlog item, not a CI gate.

For the New Stage Wizard (backlog item 005), a further real-browser pass confirmed: clicking "Blank Stage" with nothing loaded creates immediately (no dialog) and moves focus into the name field; editing the name then clicking a template button triggers the browser's real native confirm dialog, worded to name the consequence; declining it leaves the edited name completely unchanged; accepting it replaces the document with the template's two example elements, each showing "no sprite assigned" — never "invalid reference" — with no console errors; and clicking Save/Export on a wizard-created stage round-trips through the real `stage.wasm` module to a real, valid, downloadable `.def` file, confirming backlog item 005's own save/export acceptance criterion for real rather than only against the injected fake in `save-export.test.ts`.
