# Testing

## Running the suite

```sh
npm test        # single run
npm run test:watch   # watch mode
```

Vitest, `jsdom` environment. Test files are co-located with the source they test (`*.test.ts`/`*.test.mjs` next to the file it covers).

## Fixture-driven tests against the real WASM module

`src/wasm/bridge.test.ts` runs against the **real** `stage.wasm` module, not a mock — it reads `public/wasm/stage.wasm` + `wasm_exec.js` straight off disk via `node:fs` and injects them into the bridge's `fetchWasmExecSource`/`fetchWasmBytes` options, so no dev server or real network access is needed. Run `npm run wasm:download -- <version>` first if `public/wasm/` is empty (see `docs/development.md`).

A minimal `.def` fixture lives in `src/wasm/testdata/sample.def`, shared with (copied from) `stage-viewer-web`'s own fixture, itself copied from the `stage` repo's `cmd/wasm/testdata/sample.def`. `saveStage`'s tests were written after reading `stage`'s own `SerializeDef` source directly (`save.go`) rather than assumed: a non-empty original is re-parsed on every save call (a malformed original is a real `saveStage` error path, not just `loadStage`'s), and an edited stage that round-trips to the same normalized value as the original produces byte-exact output, otherwise fresh text is generated.

The stage folder input (`src/input/stage-file-input.test.ts`, `stage-file-input-view.test.ts`, and `main.test.ts`'s own store-integration cases) also runs against the real `stage.wasm` module the same way, ported verbatim from `stage-viewer-web`'s own equivalent tests — same fixture, same in-test `.sff` stand-ins (their content is never decoded by this item, so arbitrary bytes exercise name resolution and byte pass-through correctly). `main.test.ts` additionally exercises loading two different folders in sequence and asserts `stage-document-store.ts` holds only the second one — no merge, no leftover from the first.

`src/wasm/sff-bridge.test.ts` runs the same way against the real `sff.wasm` module (`public/wasm/sff/`, fetched via `npm run wasm:download:sff`), using a real `.sff` fixture (`src/wasm/testdata/v1-basic.sff`, copied from `lifebar-editor`'s own testdata) with one known sprite (group 0, image 0) — the exact metadata this fixture decodes to was obtained by running the actual module once, not derived from the mapping code under test.

## Editor screens

`characteristics-editor.test.ts` and `elements-editor.test.ts` exercise the two editing screens against plain in-memory `StageData`/`BGElement` fixtures — no WASM needed, since both screens are pure DOM-and-data-mutation logic. Coverage includes: every field pre-filled from the loaded stage; a text field committing live and a numeric field committing on blur (an invalid number is flagged inline and withheld, never silently coerced); the two bounds panels never bleeding into each other; an element's type switch showing/hiding only the fields that type uses, while preserving an unused field's own value in memory (verified by switching back); a sprite reference resolved against a real decoded sheet as valid, invalid, or not-yet-assigned (`-1,-1`, distinct from invalid); and the remove flow — a single click for an untouched, freshly-added element, an inline confirm/cancel step for one with a committed edit.

`save-export.test.ts` exercises the Save/Export button with the document store's own getter, `saveStage`, the download trigger, and `markStageDocumentSaved` all injected — covering: saving the document read fresh at click time and triggering a download with the original filename on success; clearing unsaved-changes tracking only on a successful save, never on a failed one; showing the WASM bridge's own error text (and never triggering a download) on a reported failure; and a no-op when clicked with nothing loaded. The round-trip fidelity properties themselves (byte-identical unedited, correctly-formatted-but-fresh output on an edit) are already proven at the bridge layer (`wasm/bridge.test.ts`'s own round-trip tests) and confirmed for this UI specifically by the real-browser pass below, not re-asserted here.

## Undo/redo (backlog item 008)

`command-stack-store.test.ts` and `undo-redo-controls.test.ts` (the latter ported near-verbatim from `lifebar-editor`'s own identical tests, itself running against a real `@openkakutou/web-ui-kit` `CommandStack`, not a mock) cover the shared singleton and the toolbar controls' disabled-state/refresh contract. `field-command.test.ts` covers the small shared `fieldCommand` helper: `do()` applies the new value, `undo()` restores the old one, a second `do()` (redo) re-applies the new value rather than toggling, and the given `coalesceKey` is carried through unchanged (or omitted, so the entry never coalesces).

`characteristics-editor.test.ts` and `elements-editor.test.ts` were extended to assert on the `Command` now passed to `onChange`, not just that it was called: a text field's and a numeric field's own `undo()`/`do()` revert and re-apply the committed value (checked against both the underlying data and, for the numeric case, the input's own redisplayed value); no command is pushed when a field is committed with its existing value unchanged; two different fields (`characteristics-editor.test.ts`) — and the same field on two *different* BG elements (`elements-editor.test.ts`) — get distinct `coalesceKey`s, so a rapid edit to one never merges into another's history entry; add/remove/a type switch/a sprite reference change each push a `Command` whose `undo()`/`do()` correctly reverts/reapplies; and a batch offset or sprite reassignment pushes *exactly one* `Command` whose `undo()` reverts every affected element at once — restoring each element's own distinct prior sprite, not a single shared value, for the reassignment case.

`main.test.ts`'s own undo/redo-integration cases confirm the end-to-end wiring in the real app shell: both toolbar buttons start disabled; editing the characteristics editor after creating a stage enables Undo, and clicking it reverts the edit and flips both buttons' disabled state correctly; adding then removing a BG element are each their own undo step; and creating a new stage document while the previous one has undo history clears that history (`commandStack.canUndo`/`canRedo` both `false` again) rather than carrying it across the swap.

A real regression caught only by real-browser verification (see below), now covered by two additional tests: a batch offset `Command` pushed through the *real* `CommandStack` (not a bare callback array) was applying the offset **twice** — `CommandStack.push` always invokes the command's `do()` once immediately, on top of the batch handler's own explicit first application, and the original implementation's `do()` re-added the same delta rather than replaying to an absolute target. `elements-editor.test.ts` now asserts that calling a batch offset command's `do()` a second time in a row does not double the offset, and that pushing it through a real `CommandStack` instance leaves the offset applied exactly once.

## jsdom gaps worked around in tests

`scripts/download-wasm.mjs`'s `--version` flag resolves its own `package.json` path via `fileURLToPath(import.meta.url)` (given the string form of the URL) rather than constructing a `new URL(...)` object first. Under this project's jsdom test environment, the global `URL` constructor is jsdom's own (a different realm from Node's), and `fs/promises.readFile` rejects a `URL` instance from that other realm with "The URL must be of scheme file" even though its `href` is a correct `file:` path — this sidesteps that entirely. Real `node scripts/download-wasm.mjs --version` on the command line is unaffected either way.

`src/input/`'s folder-gathering (`folder-entries.ts`) reads bytes via `FileReader` rather than `Blob#arrayBuffer()` — this project's pinned jsdom version doesn't implement it. jsdom also doesn't implement the non-standard `FileSystemEntry`/`DataTransferItem.webkitGetAsEntry()` APIs the drag-and-drop path uses at all, so `folder-entries.test.ts` exercises that walk against plain mock objects (`FileEntryLike`/`DirectoryEntryLike`) rather than real browser objects. Clicking a candidate-selection radio button in `stage-file-input-view.test.ts` reads the selection from a `"click"` listener rather than `"change"` — this project's pinned jsdom does toggle `.checked` on a dispatched `"click"` but doesn't reliably follow it with a `"change"` event.

## Beyond the test suite: real-browser verification

Passing tests are not treated as proof the UI renders correctly. The app shell was additionally driven against a real headless Chromium (dev server + Playwright) during development: confirming the toolbar reads "Stage Editor" (not carried-over "Stage Viewer" copy) with `web-ui-kit`'s actual computed styles applied, that no sidebar slot or save/dirty-state stub is rendered, and that `stage.wasm` is not fetched just from loading the page — the bridge only ever runs on demand. For the folder input specifically, the same real-browser pass drove an actual `<input webkitdirectory>` selection against a real folder on disk (Playwright's `setInputFiles` accepts a directory path directly), confirming the real WASM-backed load, the real sprite-sheet resolution, and — specific to this editor — that no premature "ready to edit" affordance appears and the status copy stays edit-neutral ("Loaded stage.def," never "Viewing").

For the characteristics and BG element editors (backlog item 003), the same real-browser pass loaded a real stage folder — a `.def` with two BG elements referencing a real `.sff` that only actually contains one of the two referenced sprites — and confirmed end-to-end: every field pre-filled correctly; editing the name and a camera bound committed for real; the element with the real sprite showed no invalid state, the one referencing the absent sprite showed the invalid-reference styling and message; switching that element's type to "anim" and back to "parallax" restored its parallax delta value unchanged; adding an element appended and auto-expanded it; removing an untouched element worked with one click; removing an edited element required the inline confirm step, and cancelling left it in place.

For save/export (backlog item 004), the same real-browser pass loaded a real stage folder, clicked Save/Export immediately (no edits), and captured the real download via Playwright's download event: byte-identical to the original file, downloaded under the original filename. It then edited the stage's name via the characteristics editor and saved again: the new download's `[Info]` section reflected the edit, and every other section round-tripped through a full fresh serialize (correctly formatted, per `stage`'s own documented contract for an edited save — see `.vibe/decisions/002-single-field-edit-produces-a-full-fresh-serialize-not-a-line-patch.md`) rather than a line-level patch. This isn't part of `npm test`; it's a manual verification step recorded in the relevant backlog item, not a CI gate.

For the New Stage Wizard (backlog item 005), a further real-browser pass confirmed: clicking "Blank Stage" with nothing loaded creates immediately (no dialog) and moves focus into the name field; editing the name then clicking a template button triggers the browser's real native confirm dialog, worded to name the consequence; declining it leaves the edited name completely unchanged; accepting it replaces the document with the template's two example elements, each showing "no sprite assigned" — never "invalid reference" — with no console errors; and clicking Save/Export on a wizard-created stage round-trips through the real `stage.wasm` module to a real, valid, downloadable `.def` file, confirming backlog item 005's own save/export acceptance criterion for real rather than only against the injected fake in `save-export.test.ts`.

For the 3D model editor (backlog item 006), a real-browser pass (software-rendered WebGL via `--use-angle=swiftshader`, since this item's live preview needs a real GPU/WebGL context no jsdom-based test can provide) caught two real bugs no jsdom test surfaced, both fixed and now covered by regression tests: (1) the live preview's `PerspectiveCamera` was never positioned from `<wuik-viewport-3d>`'s own default orbit state — three.js's own zero-value default (camera at the world origin) left the preview rendering nothing at all, fixed by reading the viewport's real `getCamera()` once construction completes (`model-preview.test.ts`'s new "reads the viewport's own starting camera state" case); (2) a field commit landing *while* the glTF was still loading was silently dropped — assigning a model then immediately editing its scale (the exact sequence a real user's fast interaction produces) left the preview stuck at the value captured when loading started, fixed by remembering the latest commit and applying it once loading actually completes (`model-preview.test.ts`'s new race-condition case). With both fixes in place, the same pass confirmed end-to-end: Camera/Scaling/Player Start Depth fields editable immediately with no model assigned; Offset/Scale fields appearing only once a model is assigned; assigning a real glTF model renders it inside `<wuik-viewport-3d>`; editing Offset X moves the rendered model live, against the *same* canvas element (no remount, confirming the incremental-update design in `.vibe/decisions/004`); assigning a `.hdr` lighting file; and removing a model requiring the inline confirm step before the reference actually clears. The only console message observed throughout was one unrelated 404 (a missing favicon — present across every OpenKakutou app, not introduced by this item).

For batch multi-select editing (backlog item 007), a real-browser pass caught two real bugs neither jsdom nor a first read of the HTML spec surfaced, both fixed and confirmed with the same pass afterward: calling `preventDefault()` on a checkbox's `click` event — for a plain click *or* a Shift-click, mouse *or* keyboard-Space alike — reverts `.checked` back to its pre-activation value once the event finishes, undoing whatever this app's own click handler had just set it to. jsdom's synthetic `dispatchEvent(new MouseEvent("click"))` does apply the native checked-toggle (unlike some real-browser untrusted-event semantics), which is exactly why `elements-editor.test.ts`'s own checkbox tests stayed green through both the broken and fixed versions of this code — the quirk is specifically about the *interaction* between a native toggle and a script-called `preventDefault()`, a combination jsdom doesn't model faithfully enough to catch. See `docs/architecture.md`'s "Batch multi-select editing" section for the fix (never call `preventDefault` on the checkbox's own `click` event, on either selection path). With the fix in place, the same pass confirmed end-to-end, against a stage with five BG elements: a plain click and a real keyboard Tab-then-Space both select a single row correctly; a mouse Shift-click and a keyboard Shift-Space both select the full contiguous range from the last individually-selected row, with every row in the range (not just the endpoints) correctly checked and highlighted; the toolbar's Apply buttons start disabled and enable only once a real offset or sprite is chosen; applying an offset moves only the selected rows' `startX`/`startY`, by the given delta, leaving every other row untouched; removing a selected row updates the toolbar's own count with no stale reference to the removed element; and Clear Selection empties the selection and hides the toolbar. No console errors throughout.

For undo/redo (backlog item 008), a real-browser pass caught a real bug no unit test surfaced: applying a batch position offset moved the selected elements by *twice* the entered delta on the very first click — `CommandStack.push` calls the pushed command's `do()` once immediately in addition to the batch handler's own explicit first application, and the original `do()` re-added the same delta instead of replaying to an absolute target (fixed as described above, and now covered by regression tests). The unit tests missed it because they inspected the pushed `Command` object directly rather than routing it through a real `CommandStack.push`. With the fix in place, the same pass confirmed end-to-end: both toolbar buttons start disabled; creating a stage then editing its name enables Undo; clicking Undo reverts the name and correctly flips both buttons' disabled state; clicking Redo re-applies it; adding a BG element then clicking Undo removes it as a single step; and selecting two BG elements, applying a batch position offset, then clicking Undo *once* reverts both elements together rather than requiring one undo per element. No console errors throughout.

For keyboard shortcuts (backlog item 009), a real-browser pass caught two real bugs neither jsdom nor a first read of the acceptance criteria surfaced, both fixed and confirmed with the same pass afterward: (1) the "Add element" button's own shortcut-hint tooltip went stale/empty after the very first add/remove/type-switch/batch action — `elements-editor.ts`'s own internal `rerender()` closure (which every one of those user actions calls directly, recreating the button each time) bypasses `app`'s rerender wrapper entirely, so a rebind that only ran from that wrapper never reached the freshly created button; fixed by also rebinding from the `onChange` callback that fires after every committed edit, structural or not (now covered by a `main.test.ts` regression test). (2) rebinding an action to a new key inside the shortcuts panel could immediately re-fire that same action — `<wuik-shortcuts-panel>`'s own rebind-capture calls `preventDefault()` on every key it captures but never `stopPropagation()`, so the very keydown that just set the new binding also bubbles to `app`'s own `window`-level listener and gets dispatched as a live keypress against the binding that now (as of that same event) owns it; most concerning for Delete Selection, which has no confirm step of its own — observed as an unexpected "Saved stage.def." status appearing right after rebinding Save/Export to a fresh key, and confirmed via a dedicated check that rebinding Delete Selection while an element was selected did not also delete it. Fixed by having the dispatcher no-op on an already-`preventDefault()`-ed event (now covered by an `app-shortcuts.test.ts` regression test). With both fixes in place, the same pass confirmed end-to-end, against a fresh blank stage: the shortcuts panel starts expanded, listing all five actions with their correct default keys; Ctrl+Shift+A adds a BG element with a correctly live tooltip; Ctrl+Z/Ctrl+Y undo/redo it; selecting the element then pressing Delete removes it instantly with the expected status message, and Undo restores it *and* its prior selection state; pressing Delete while focus is in a real text field does nothing; and rebinding Save/Export via the panel updates its toolbar tooltip immediately, with no accidental extra fire and no console errors throughout.
