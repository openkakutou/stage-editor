# Testing

## Running the suite

```sh
npm test        # single run
npm run test:watch   # watch mode
```

Vitest, `jsdom` environment. Test files are co-located with the source they test (`*.test.ts`/`*.test.mjs` next to the file it covers).

## Fixture-driven tests against the real WASM module

`src/wasm/bridge.test.ts` runs against the **real** `stage.wasm` module, not a mock — it reads `public/wasm/stage.wasm` + `wasm_exec.js` straight off disk via `node:fs` and injects them into the bridge's `fetchWasmExecSource`/`fetchWasmBytes` options, so no dev server or real network access is needed. Run `npm run wasm:download -- <version>` first if `public/wasm/` is empty (see `docs/development.md`).

A minimal `.def` fixture lives in `src/wasm/testdata/sample.def`, shared with (copied from) `stage-viewer-web`'s own fixture, itself copied from the `stage` repo's `cmd/wasm/testdata/sample.def`. `saveStage`'s tests were written after reading `stage`'s own `SerializeDef` source directly (`save.go`) rather than assumed: a non-empty original is re-parsed on every save call (a malformed original is a real `saveStage` error path, not just `loadStage`'s), and an edited stage that round-trips to the same normalized value as the original produces byte-exact output, otherwise fresh text is generated.

## jsdom gaps worked around in tests

`scripts/download-wasm.mjs`'s `--version` flag resolves its own `package.json` path via `fileURLToPath(import.meta.url)` (given the string form of the URL) rather than constructing a `new URL(...)` object first. Under this project's jsdom test environment, the global `URL` constructor is jsdom's own (a different realm from Node's), and `fs/promises.readFile` rejects a `URL` instance from that other realm with "The URL must be of scheme file" even though its `href` is a correct `file:` path — this sidesteps that entirely. Real `node scripts/download-wasm.mjs --version` on the command line is unaffected either way.

## Beyond the test suite: real-browser verification

Passing tests are not treated as proof the UI renders correctly. The app shell was additionally driven against a real headless Chromium (dev server + Playwright) during development: confirming the toolbar reads "Stage Editor" (not carried-over "Stage Viewer" copy) with `web-ui-kit`'s actual computed styles applied, that no sidebar slot or save/dirty-state stub is rendered, and that `stage.wasm` is not fetched just from loading the page — the bridge only ever runs on demand. This isn't part of `npm test`; it's a manual verification step recorded in the relevant backlog item, not a CI gate.
